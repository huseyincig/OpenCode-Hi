# Execution Benchmarks

OpenCode-Hi includes a deterministic in-process policy benchmark covering the nine representative scenarios covered by the current deterministic benchmark contract: simple local work, repository-convention reuse, complex cross-module work, failed verification, long sessions, human-gated work, long-running processes, multi-model work, and multi-agent work.

The canonical machine-readable receipt is `data/validation/benchmarks-0.1.0.json`, generated by `node scripts/run-benchmarks.mjs` after the TypeScript build.

## Claim boundary

These are deterministic policy simulations. They measure Hi decisions and bounded execution-shape counters such as agent count, context characters, actions, retries, verification actions, and synthetic elapsed units. They **do not** claim real provider token billing, model latency, OpenCode process latency, or external-host behavior. Real OpenCode/provider observations require a host receipt and remain `PENDING_EXTERNAL` when the host is unavailable.

The benchmark is useful for regression because it proves properties such as: trivial work stays single-agent; context governance reduces discardable context while preserving protected state; non-material human prompts are reduced; identical retry loops are not rewarded; and independent multi-stream work may fan out only when the topology policy identifies a material benefit.

## Scheduler and model feedback calibration

O1 extends the deterministic receipt with scheduler units/events for queue wait, provider/model saturation, task-duration units, retries, context size, same-session reuse benefit, and write-conflict serialization. These remain in-process policy measurements, not provider wall-clock latency or billing. The O1 baseline does not justify adding priority, aging, provider-circuit, or resource-pressure scheduling policy.

O3 model feedback is a derived current-Mission projection, not a persistent model reputation database. Only the newest 12 terminal workers matching the current role/category are eligible. Observations may include success/failure, retry count, structured verification outcome, and latency only when worker start/completion timestamps exist. A single sparse observation is `insufficient` confidence and contributes no success/failure/verification score adjustment; repeated observations/retries can reach bounded low/medium/high confidence. Smart Select continues to compute expected completion cost from declared model cost/turn/context properties and bounded retry history; observed latency is diagnostic metadata rather than fabricated provider cost.
