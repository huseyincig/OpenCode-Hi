for AI-assisted software engineering.

It is NOT primarily trying to maximize:

- autonomy
- agent count
- prompt complexity
- reasoning length
- model strength

================================================================================
13. COMPLETION AND STOP
================================================================================

Completion must remain deterministic and evidence-aware.

Conceptual completion contract:

requested outcome satisfied
AND required obligations closed
AND required verification evidence fresh
AND no blocking evidence unresolved
AND no pending authority decision
AND no pending task
AND no pending worker
AND no pending required child result
AND no pending required process
AND no pending rollback
AND CompletionAdjudicator approves
→ STOP

STOP is authoritative.

After STOP, do not perform speculative:

- extra refactoring
- broad review
- documentation expansion
- optimization
- exploration

unless explicitly required by an open obligation.

14. SIX INDEPENDENT ADAPTIVE EXECUTION AXES
================================================================================

OpenCode-Hi must explicitly separate six decision dimensions.

1. ROLE
   Who should perform the work?

2. SKILL
   Which methodology is necessary?

3. MODEL / TOOL
   Which capability is sufficient?

4. EXECUTION DEPTH
   How much reasoning, planning, exploration, delegation and verification?

5. CONTEXT DEPTH
   How much information is necessary?

6. ISOLATION DEPTH
   How much environmental protection is necessary?

These dimensions must NOT be collapsed.

Examples of forbidden coupling:

complex task
≠ automatically strongest model

review role
≠ automatically dedicated agent

specialist role
≠ automatically separate session

skill available
≠ automatically activated

high risk
≠ automatically entire repository context

multi-agent capability
≠ automatically multi-agent execution


================================================================================
15. ROLE, AGENT AND MODEL ARE DIFFERENT THINGS
================================================================================

The implementation must model:

ROLE
AGENT INSTANCE
MODEL
TOPOLOGY

as separate concepts.

A role does not imply a dedicated agent.

An agent does not imply a fixed model.

A model does not imply a role.

Required supported execution forms:

A. single agent + single model

B. single agent + multiple logical roles

C. multiple agents + one shared model

D. multiple agents + multiple models

E. multiple instances of the same role

Example:

single primary agent:

roles:
- repository exploration
- coding
- verification

This is valid when task complexity does not justify delegation.

Another valid topology:

manager
├── explorer
├── coder
└── reviewer

All may use one model.

Another:

manager  → model A
explorer → model B
coder    → model C
reviewer → model D

Another:

coder instance A → backend
coder instance B → frontend
coder instance C → tests

Do not confuse:

"same agent template used multiple times"

with:

"one agent performing multiple roles"

18. ADAPTIVE EXECUTION PATHS
================================================================================

At minimum implement coherent support for:

DIRECT
EVIDENCE
PLANNED
ESCALATED

DIRECT
------

Use when:

- task is clear
- scope is local
- uncertainty is low
- impact is reversible
- failure impact is low
- verification is cheap

Default direct trajectory:

assess
→ execute
→ targeted verify
→ STOP

Typical direct defaults:

planner = 0
delegation = 0
specialist = 0
broad repository scan = 0
memory lookup = 0
reviewer = 0

EVIDENCE
--------

Use when a material uncertainty can change the implementation decision.

Trajectory:

identify decision-changing uncertainty
→ acquire minimum relevant evidence
→ decide
→ execute
→ verify

Do not perform broad research merely because uncertainty exists.

Ask:

"What information could materially change the next decision?"

PLANNED
-------

Use when real coordination or sequencing is necessary.

Triggers include:

- cross-module dependency
- multiple coupled changes
- migration sequencing
- interface/contract interaction
- rollback complexity
- stateful coordination

Planning must be:

- bounded
- dependency-oriented
- implementation-oriented
- acceptance-oriented

Avoid planning ceremony.

ESCALATED
---------

Escalation may use:

- stronger model
- specialist role
- additional agent
- broader context
- broader evidence
- review
- increased verification
- stronger isolation

Escalation MUST have a recorded reason.

Capability availability alone is not an escalation reason.
